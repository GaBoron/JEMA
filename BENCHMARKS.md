# Benchmarks

The six full-length six-stereo-track inputs total 2,789,107,248 bytes of Float32 PCM. With adaptive prediction enabled, JEMA stores them in 1,696,471,794 bytes, a 39.18% reduction from PCM and a 10.72% reduction from the earlier encoder. Its files are 2.33–5.61% smaller than lossless WavPack's very-high preset on the three full-length comparisons.

### Adaptive playback workload

The windowed benchmark uses the same all-track PCM geometry and machine as the earlier measurements. A typical read requests 88200 frames and the application maintains approximately a third of a second of prefetch lead. An 80 ms P99 for that two-second window was used as a local screening budget, leaving room for I/O variability, scheduling, and other work. This budget is specific to the tested workload and hardware.

| Encoder or source | I/O regime | 14700-frame P99 | 88200-frame P99 | Worst 88200-frame read |
| --- | --- | ---: | ---: | ---: |
| Raw PCM | Warm | 0.216 ms | 1.250 ms | 1.532 ms |
| Earlier JEMA | Warm | 5.874 ms | 15.611 ms | 23.640 ms |
| Adaptive JEMA, scalar predictor | Warm | 8.079 ms | 25.293 ms | 37.714 ms |
| Raw PCM | Unbuffered | 0.600 ms | 1.911 ms | 2.066 ms |
| Earlier JEMA | Unbuffered | 6.873 ms | 19.875 ms | 26.010 ms |
| Adaptive JEMA, scalar predictor | Unbuffered | 9.777 ms | 38.246 ms | 50.694 ms |

Default adaptive sequential decoding with the scalar predictor sustained 222 MiB/s warm and 188 MiB/s with the OS data cache bypassed. Six stereo tracks at 44.1 kHz require 2.02 MiB/s. Peak working set was approximately 55 MiB in both runs, including the process runtime, caller's span, and benchmark buffers. Each random two-second request read an average of 0.67 encoded bytes per requested PCM byte. Its decode amplification remained 1.09× at the same block geometry.

The block-size and Zstandard level sweep uses `stem-01` and the default maximum order of 16. Rows with other settings use 500 unbuffered requests. The default uses 1000 requests.

### Higher compression and AVX2 decoding

The deep predictor option tries an additional sectional candidate with up to 32 coefficients per lane. The reference decoder uses AVX2 for the integer dot products of order eight or greater on compatible hardware. It preserves the same arithmetic and archive bytes. The following 500-request measurements use that path, unbuffered I/O, and 88200-frame windows.

| ID | Block frames / level | Predictors | Stored bytes | Reduction from current default | P99 | Max |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| stem-01 | 8192 / 5 | Standard | 202,432,688 | — | 50.041 ms | 60.692 ms |
| stem-01 | 8192 / 5 | Deep | 202,181,160 | 0.12% | 47.372 ms | 57.459 ms |
| stem-01 | 16384 / 13 | Standard | 201,852,143 | 0.29% | 44.853 ms | 55.670 ms |
| stem-01 | 32768 / 9 | Standard | 201,944,406 | 0.24% | 61.070 ms | 75.595 ms |
| stem-03 | 8192 / 5 | Standard | 310,032,759 | — | 51.971 ms | 72.634 ms |
| stem-03 | 8192 / 5 | Deep | 308,961,140 | 0.35% | 45.467 ms | 48.969 ms |
| stem-06 | 8192 / 5 | Deep | 281,397,441 | 0.74% | 49.444 ms | 65.250 ms |
| stem-06 | 16384 / 13 | Deep | 280,484,108 | 1.07% | 46.911 ms | 85.797 ms |

The most compact measured `stem-06` archive recovered every input byte. In four back-to-back runs of 300 identical two-second requests on that archive, scalar P99 was 82.501–89.452 ms and AVX2 P99 was 48.104–50.405 ms. The AVX2 maxima were 72.336 and 73.684 ms in those runs. The high settings give the smallest measured archive on this source and stay within the local P99 screening budget on AVX2. These values are from offline reads. In-host playback and scheduling under concurrent application load remain unmeasured.

```sh
dotnet src/Jema.Tool/bin/Release/net8.0/Jema.Tool.dll encode stems.f32le compact.jema 44100 2,2,2,2,2,2 16384 13 --deep-prediction --workers=4
dotnet research/Bench/bin/Release/net8.0/Bench.dll jema stems.f32le compact.jema 500 4096 88200
```

### Encoding time budget

The encoding target is 60 elapsed seconds per minute of input audio. The earlier single-worker default encoded the six full-length files in 16.14–18.26 seconds per minute. The four-worker high-compression configuration uses 16384-frame blocks, Zstandard level 13, and deep prediction. The timed command includes process startup, PCM reads, compression, and archive writes. The separate verification pass is outside the encode interval.

All three full-length encodes passed a complete PCM byte comparison. Both `stem-06` archives match byte for byte, so its earlier decode measurement also applies to the parallel encode. Clock time depends on available CPU capacity, disk I/O, and concurrent work.

For the six-stem input, FFmpeg decodes each original to stereo `f32le` at 44.1 kHz. The upstream separator uses checkpoint revision `a443a2985534b3bc815ef54a5d446c6a0390f974`, CUDA Float16 inference, and its ordinary overlap setting. Its output order is vocals, drums, bass, guitar, piano, and other. The second separator takes seconds 10–55 from `stem-02`'s mix, uses WAV FLOAT input and output, and interleaves vocals before instrumental. Private song audio and metadata remain outside the repository. [Separation worker](https://github.com/GaBoron/SPW-Track-Mix/blob/5f18418/src/main/resources/trackmix/separate.py) · [Audio Separator](https://github.com/nomadkaraoke/python-audio-separator)

For AlbumDB, the inputs are `bass.wav`, `guitar_acoustic_r.wav`, `viola.wav`, and `vox_outro.wav` in `stems_raw/10 It Ain't Easy (To Mend A Heart)`. Decode each with `ffmpeg -i INPUT.wav -ar 48000 -ac 1 -f f32le OUTPUT.f32le`, truncate to the shortest lane, and interleave in that order. The DSP case computes `f32(f32(0.7937*x[t]) - f32(0.1731*x[t-1]))` per lane with a zero initial predecessor and Float32 coefficients. The Chalmers WAV already contains Float32 PCM. Extract it with `ffmpeg -i INPUT.wav -map 0:a:0 -c:a copy -f f32le OUTPUT.f32le`. It provides recorded and calibrated Float32 data. The device-native capture representation was outside this measurement. [AlbumDB](https://zenodo.org/records/19683001) · [Chalmers dataset](https://zenodo.org/records/16901844)

## Earlier random access and resource use

Measurements use `stem-01` on Windows build 26300, Intel Core i9-14900HX, 32 GiB RAM, UMIS RPJYJ1T24MLR1HWY NVMe SSD, and .NET 8.0.34 x64. The separation environment uses FFmpeg `n8.1.3-18-g46d899d7a0`, Audio Separator 0.48.0, Torch 2.10.0+cu128, and an RTX 4060 Laptop GPU. Compression and playback-path measurements use the CPU. Baseline tools use Python 3.13, NumPy 2.4.6, python-zstandard 0.25.0, Pcodec 1.1.0, and WavPack 5.9.0.

The warm test reads the complete file first. The unbuffered test uses Windows `FILE_FLAG_NO_BUFFERING` with 4096-byte alignment to bypass the OS data cache. SSD controller and filesystem metadata caches can remain warm. The raw comparator reads the same requested frame ranges into a byte span. The JEMA run includes index lookup, decompression, inverse prediction, PCM CRC, and copying partial blocks. Random rows contain 1000 uniformly sampled starts per window. Open-and-first rows contain 128 fresh opens followed by the first second of PCM. Codec and OS paths receive an untimed initial call. ### WavPack seek comparison

The WavPack library benchmark uses the public seek and unpack functions with Float32 normalization disabled. The same file, warm cache preparation, window sizes, and request counts are used for both WavPack presets. The Python and .NET harnesses use different deterministic samples from the same uniform start distribution. WavPack output words were compared with the original after every measured read. ## Reproduction

```sh
dotnet build src/Jema.Tool -c Release
dotnet build research/Bench -c Release
dotnet src/Jema.Tool/bin/Release/net8.0/Jema.Tool.dll encode stems.f32le stems.jema 44100 2,2,2,2,2,2
dotnet src/Jema.Tool/bin/Release/net8.0/Jema.Tool.dll verify stems.jema stems.f32le
dotnet research/Bench/bin/Release/net8.0/Bench.dll raw stems.f32le stems.jema 1000 0
dotnet research/Bench/bin/Release/net8.0/Bench.dll jema stems.f32le stems.jema 1000 0
dotnet research/Bench/bin/Release/net8.0/Bench.dll jema stems.f32le stems.jema 1000 4096
python research/compare.py stems.f32le 44100 2,2,2,2,2,2 comparison --wavpack-dir WAVPACK_DIR --tool src/Jema.Tool/bin/Release/net8.0/Jema.Tool.dll
python research/wavpack_access.py WAVPACK_DLL comparison/whole.wv stems.f32le
```

The optional final benchmark argument selects one random window size in frames. Append `--no-adaptive` to the encode command to reproduce the earlier JEMA mode set. The Python tools require NumPy and python-zstandard. The block comparator also requires Pcodec. The comparison creates a new output directory and can contain several copies of the input size. Windows WavPack binaries are available from the [WavPack release](https://github.com/dbry/WavPack/releases/tag/5.9.0).

The current corpus covers two separator architectures, studio stems, a calibrated Float32 recording, and synthetic exact-loop and high-entropy controls. Its scope is limited to the measured tracks and the Windows reference machine. Hardware-native capture provenance, other operating systems, concurrent playback, and external application integration remain outside the measured scope.
